### 1.1 v1103 が扱う問い

**ESDE の揺れから辿った連想先の Atom 候補群を 48 次元空間に置いたとき、密度の偏り (クラスタ) が生じるか。生じるなら、その偏りは応答 Atom 群を絞る構造的指標として機能するか。**

### 1.2 なぜ段 4-c が「決定」であり、それが規律違反でないか

段 4-c は決定である — 連想先の候補群から応答 Atom 群を絞る。会話の応答は最後に具体的な形を取るため、候補を全部並べたままでは応答にならない。

この「決定」は ESDE の規律違反ではない (段 4 足取り点検 §0 / §4.2-4.3)。Taka が明示したとおり、Genesis の「決定を避ける」を ESDE 全体の哲学に昇格させたのが誤りで、ESDE は決定論の半身 (Language、326 Atom と 3 万語を決定した) を最初から持つ。段 4-c で決定が起きることは裏切りでも侵入でもない。

外部評価関数の侵入を避ける条件は「argmax を取らない」ではなく「決定を loss/reward でなく構造的指標で行う」こと (段 4 足取り点検 §4.2)。v1103 の段 4-c は 48 次元密度の偏りという構造的指標で応答 Atom を絞る — 研究者も外部評価も「これが良い応答」と選ばない。これが研究手法アップデートの「際立ちの掬い取り」の段 4-c 版。

### 1.3 v1103 が扱わないもの (§0.3 の再掲・確定)

## 2. 観察設計 — 段 4-b → 4-c → 4-d の足取り

Language 側素材 §7 の見取り図を基に、観察設計を組む。これは Genesis 側 × Language 側の素材を噛み合わせた足取りであり、2 AI 監査で詰める。

### 2.1 入力 (段 4-a、v1102 が提供)

段 4-c 点検の入力は、v1102 primary table の「受け手構造別の応答 profile」。v1102 が出した CID n_core / Integration 構成 / qc_regime × atom 像。揺れ単体でなく、v1102 が構造化したものを使う (段 4 足取り点検 §4.4 条件 D)。

### 2.2 48 次元の疎性の前処理 (段 4-b の前、必須の足場固め)

Language 側追補メモ (2026-05-20) で確定した必須ステップ。**素直な 48 次元 cosine は使えない** — Atom は 48 次元すべてに値を持たない。`esde_dictionary.json` の定義レベルで各 Atom は関係する axes/levels だけを記述として持ち、batch_report.md 実測でも平均 Nonzero は 14.5 / 48。326 Atom × 48 次元の空間は密な行列でなく疎な空間。疎性を考慮せず素直に cosine を取ると 2 つの問題でノイズが乗る。

**問題 1 — ゼロの意味が二義的**。あるスロットのゼロが (a) その軸と本当に無関係 (測定結果「ここには立たない」) なのか、(b) 定義時にその軸を記述しなかっただけ (未測定) なのか、二通りに読める。未測定のゼロと測定済みのゼロを同じ 0 として cosine に入れると、たまたま同じ軸で「未記述」だった 2 Atom が「同じ場所にいる」と誤判定されうる。

**問題 2 — 疎な空間での cosine は重なり軸数に依存**。Atom A が 14 軸、B が 16 軸に立ち重なりが 5 軸のとき、48 次元 cosine はその 5 軸でほぼ決まる (残り 43 軸は両方ゼロで寄与しない)。重なり 5 軸のペアと重なり 20 軸のペアの cosine が、信頼度がまったく違うのに同じ「類似度」として並ぶ。

→ 段 4-b (連想) ・段 4-c (密度) より前に、48 次元空間の前処理を必須ステップとして置く。前処理の中身:

1. **ゼロの意味の確定** — Code A が `*_a1_final.jsonl` の `normalized_scores` の実体を見て (a)/(b) を確定する。48 キー全部あって一部が 0.0 なら (a) 測定結果、立っている軸のキーしかないなら (b) 未測定。Language 側 Web Claude は記憶ベースでは確定できない、実データで確定する。
2. **疎性に対応した近傍・密度の計算方式の選定** — 素直な cosine でなく、以下 3 対処のいずれかを Code A が実データ (ゼロの意味、Nonzero 軸数分布、軸ごとの値分布) に基づいて選定する:
   - 対処 A: 軸の重なりを明示的に扱う (両方が立つ軸数とその一致度を分け、重なり軸が少ないペアは信頼度を下げる)
   - 対処 B: 疎性を特徴にする (値の cosine でなく「どの軸に立つか」の軸パターンの Jaccard で連想地形を作る、v1100 の Jaccard 照合と同型)
   - 対処 C: 軸ごとに正規化 (batch_report.md が示した軸ごとの偏り — ontological 軸 material レベルの重力場等 — を補正してから密度を測る)
3. 前処理結果 (ゼロの意味、選定した対処、計算方式) を Genesis 側 Web Claude と Language 側 Web Claude に報告してから段 4-b に進む。

この前処理は距離を遠くするものではない。段 4-c 点検を始めるときの最初の作業が「48 次元空間をどう扱うか決める」になるというだけ。前処理を飛ばすと段 4-c の点検結果がノイズに埋もれて判定不能になるため、必須の足場固め。以降 §2.3 以降で「48 次元近傍」「48 次元密度」と書く箇所は、すべて「(疎性前処理を経た計算方式での) 48 次元近傍/密度」を指す。

### 2.3 段 4-b — 連想を辿る

応答 profile の atom を起点に、連想先の Atom 候補群を辿る。連想地形は二層:

- **離散リンク** — Constitution Couple 関係 (6 件、cross-category 共鳴)。人が構造決定した強いリンク。同カテゴリ内に閉じやすい 48 次元近傍に対し、Couple は遠距離カテゴリへ飛ぶ橋。
- **連続地形** — A1 48 次元近傍 (疎性前処理を経た計算方式による)。`atom_centroids_48d.csv` の 326 Atom centroid で、起点 Atom と近い上位 k 個。32,666 語の実測共鳴値が作る連続地形。素直な cosine でなく §2.2 で選定した対処 A/B/C の方式で近傍を引く。

連想先 = Couple リンク先 ∪ 48 次元近傍。

**設計制約 (Projection 失敗の教訓、Language 側素材 §6.2)** — 段 4-b/4-c は単一の 48 次元空間の中だけで閉じる。Projection が失敗したのは MiniLM 384 次元空間で近傍を引いて Atom 48 次元空間に持ち込んだ、空間をまたぐ粗い橋渡しのため。v1103 は Genesis の cid も Language の Atom も A1 の語もすべて同じ 48 次元にいる、その単一空間の中だけで連想と絞りを完結させる。MiniLM 等の異種埋め込み空間を経由しない。

### 2.4 段 4-c — 48 次元密度の偏りで絞る (本主題の核心)

段 4-b で得た連想先 Atom 候補群を 48 次元空間に配置し、密度の偏りを検出する。

1. 連想先 Atom 候補群を 48 次元に配置
2. 候補群の 48 次元分布の密度を見る — 均等に散れば「際立ちなし」、ある領域に密集すれば「際立ち」
3. 密集領域 (クラスタ) を検出
4. 密集を作る Atom の信頼度を品質フラグで重みづけ (§2.5)
5. Constitution の構造制約を適用 (§2.6)
6. 残った Atom 群を応答候補とする

密度の偏りの検出方法 (クラスタリングの具体的アルゴリズム、密度の定義) は 2 AI 監査 + Code A 認識確認で詰める論点 (§3 論点 1)。閾値は分布から構造的に選定し恣意的に置かない (研究手法アップデート、Step G の gini bin 選定と同型)。

**密度指標を単一化しない (GPT 監査 1)** — 「密度」を一つの指標に絞らない。少なくとも以下 4 種を分けて並列に出す:
- raw 密度 — 連想先候補そのものの 48 次元分布の密度
- quality-weighted 密度 — A1 品質フラグ (§2.5) で重みづけした密度
- constitution-adjusted 密度 — Constitution 制約 (§2.6) を適用した後の密度
- receiver-conditioned 密度 — 受け手構造別 (CID n_core / Integration 構成) に分けた密度

単一の密度値で「際立ちが出た/出ない」を語ると、v1101 核心発見「観察単位で像が割れる」・留保 #33 系列の轍を踏む。4 種を並列に持ち、密度指標によって際立ちの見え方が違うこと自体を観察に含める。

**k を単一固定しない (GPT 監査 2)** — 段 4-b の 48 次元近傍の k (上位何個まで) を一つに固定しない。複数の k で multi-k sensitivity を行い、k を変えても安定して現れる cluster (k に頑健) と、特定の k でしか出ない cluster (k 依存) を分けて記録する。k に頑健な cluster は段 4-c の構造的指標としてより信頼でき、k 依存の cluster は k の選び方のアーティファクトの疑いがある。これも「単一の設定で語らない」(留保 #33 系列) の適用。

### 2.5 偽の際立ちを弾く — A1 品質フラグ

48 次元密度が際立ちを示しても、その密度を作る Atom centroid 自体の信頼度に差がある (Language 側素材 §5)。低品質な centroid が作る際立ちは偽かもしれない。

A1 品質フラグで信頼度を重みづける:
- focus rate (Atom の語が特定スロットに集中する度合い、平均 0.578) — 高いほど centroid が信頼できる
- revise 率 — 高い Atom (PRP.multiple 52.7% 等) は境界が曖昧、際立ちを弱める
- diffuse / mass fail — 多い Atom は centroid がぼやけている

**品質フラグは削除でなく重みづけ・併記 (GPT 監査 3)** — 品質の低い Atom を候補から削除しない。削除すると「研究者が低品質を理由に切る」= 神の手 (研究手法アップデート §1、v1102 でサンプル数除外を退けたのと同型) になる。品質フラグは候補を消すのでなく信頼度の重みとして使い、§2.4 の quality-weighted 密度として raw 密度と併記する。低品質 Atom が作る際立ちは「重みが低い際立ち」として残し、読む側が raw と quality-weighted の差を見られるようにする。

3 条件再観測の高品質サブセット (6,025 語) は **補助実験** として扱う (GPT 監査 3)。全体 (32,666 語) での点検を主とし、高品質サブセットは「全体でノイズに埋もれた場合にシグナルを確認する補助」。高品質サブセットを主にすると、それ自体が「研究者が高品質だけ見る」選別になる。主は全体、補助がサブセット。

偽の際立ちを弾く判断も研究者の主観でなく品質フラグという構造指標で行う — ただし「弾く」は「削除」でなく「重みを下げて併記」。

### 2.6 Constitution の構造制約

段 4-c の絞りに Constitution の 3 種を制約として使う。**いずれも候補の削除条件にしない (GPT 監査 4)** — 削除は神の手になる。

- Merge (3 件) — 同一概念とみなす 2 Atom は候補集合で統合 (重複排除)。これは削除でなく「2 つを 1 つの概念単位として数える」統合操作。
- Subsume (1 件) — 階層親子。子が際立ったとき親も候補に併記する (親子併記)。どちらかを消すのでなく親子関係を明示したまま両方残す。
- Monitor (7 件) — 構造不安定な Atom。**削除条件でなく caution flag**。Monitor 指定の Atom が際立っても候補から消さず、「構造が不安定という注意フラグつきの際立ち」として併記する。読む側が Monitor フラグを見て解釈できるようにする。

Constitution 制約を適用した密度は §2.4 の constitution-adjusted 密度として、raw 密度と併記する。

### 2.7 段 4-d — 確率分布で出力

段 4-c が絞った応答 Atom 群を確率分布で出力する。argmax は取らない (v1101a 箱 3、Aruism 対称性、全出力候補・確率表記)。

**出力の正体 (GPT 監査 7)** — この出力 (response_atom_distribution と呼ぶ) は自然言語応答ではない。段 4-c が 48 次元密度の偏りで絞った応答 Atom 群の候補確率分布である。「応答」という語を自然文と取り違えないこと (v1102 §1.1 の「応答 = 内部 profile」と同じ予防線)。自然文になるのは段 5a (Atom→単語、Lexicon) と段 5b (単語→文、LLM 外注) を経た後であり、v1103 はそこに進まない。v1103 の出力は「段 4-c の候補分布」までで、それ以上でない。

ただし「確率分布なら決定していない」ではない (段 4 足取り点検 §4.2)。決定はパイプラインのどこかで必ず起きる。段 4-d が確率分布を出すのは規律であって、決定の不在を意味しない。v1103 の段 4-c が行った「絞り」が決定であり、それは §1.2 のとおり構造的指標による決定なので外部評価関数の侵入ではない。

### 2.8 出力先の確認 (段 5a、点検対象外)

段 4-c が応答 Atom 群を出せば、その先 (段 5a) は Lexicon Core pool で埋まる (32,666 語の完成データ)。v1103 では段 5a を実装しないが、「段 4-c の出力先が既にある」ことを確認しておく。段 4-c の点検は出力先の心配なく行える。
