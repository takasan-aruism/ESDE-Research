## 0. なぜこの指針が必要か

ESDE では Taka の比喩的・哲学的表現が **探索を前進させる役割** を持つ。

しかし AI は字面に強く引っ張られるため、そのままでは:
- 意味の盛りすぎ
- 仕様の取り違え
- 過剰な一般化

を起こす。

本指針は、**比喩を抑圧せず、かつ実装精度を保つ**ための共通原則。

---

## 1. 監査の基本姿勢 (原則 4 項)

| 原則 | 内容 |
|---|---|
| 1.1 探索を削がない | 監査は保守ではなく、探索を壊さず**検証可能な形へ落とす**ため |
| 1.2 比喩を即否定しない | 強い表現は**探索の起点**、語の強さだけで弱めない |
| 1.3 先に切り分ける | 比喩 / 仮説 / 実装仕様 / 観察結果 / 外部説明 のどれか判定 |
| 1.4 「何を壊すか」だけ厳密 | 物理層、bit-identity、仕様と観察の混同、比喩の即仕様化、未観察の確定記述 |

### 1.4 で厳密に制動すべき場面

- 物理層を壊す (v19g_canon 等を変更する提案)
- 既存の bit-identity を壊す (v9.14 baseline CSV の破綻)
- 仕様と観察を混同する (観察事実を仕様として書く)
- 比喩をそのままコード要件として扱う
- Summary / 原本に未観察の意味を確定的に書き込む

これ以外では、監査は**弾力的**に振る舞う。

## 2. 読者別の監査方針

**監査・資料作成は必ず「誰向けか」を先に確認する**。

### 2.1 Taka 向け資料 (議論、Phase 議論記録)

- 比喩の推進力を**尊重**する
- 強い表現 (摂食行動、穴、ある/ない、原資) はそのまま使ってよい
- 必要なら脚注で「コード上は何に対応するか」を補う

### 2.2 AI 向け資料 (Code A 指示書、Claude/Gemini 参照資料)

- 字面誤読を避けるため**一段操作的に落とす**
- 目的は表現の弱体化ではなく**誤実装の防止**

置換例:

| Taka 向け表現 | AI 向け表現 |
|---|---|
| 摂食行動 | 片方向 E3 接触 / ghost 由来情報取得イベント |
| 他者理解 | 他 cid 由来情報の取得 |
| 自己の成立 | 自己読み条件の整備 |
| 意識の原資 | Q 消費に対応づけられた認知的資源仮説 |

### 2.3 外部向け資料 (将来の発表等)

比喩・仮説・結果を**最も厳密に分ける**。強い表現を残す場合は必ず:
- それが比喩であることを明示
- どの観察事実に対応するかを明示
- 何が未確定かを明示

### 2.4 Summary / 原本

Taka 発言は**引用形式 (>) で原文保存**。併記方式:

```
「摂食行動」(片方向 E3 接触の比喩、Taka 2026-04-23)
```

このラベル方式で、原文の力を保ちつつ AI の誤読を防ぐ。

## 3. 比喩表現への監査ルール

### 3.1 禁止すべき監査

> 「その言い方は強すぎる。もっと弱く言うべきだ。」

これは**情報量が少なく、探索の利益も不明瞭**。監査として機能しない。

### 3.2 推奨される監査の形式

比喩にコメントする時は 4 項目を必ず書く:

1. **この表現はどの層か** (比喩 / 仮説 / 実装仕様)
2. **そのまま残す利点は何か** (Taka 直感の保持、探索の焦点維持)
3. **変えるなら、誰向けに、何のために変えるか**
4. **置換語の具体的メリットは何か**

### 3.3 良い監査と悪い監査の例 (摂食行動)

**悪い監査**:
> ESDE は生物ではないので、摂食行動という言い方は不適切

**良い監査**:
> - Taka 向け議論資料では「摂食行動」を残す (探索推進力あり)
> - AI 向け資料では「生物学的摂食」への誤補完リスク
> - AI 向けには「片方向 E3 接触」または「ghost 由来情報取得イベント」へ置換
> - 置換の目的は弱体化ではなく、読者依存の誤読防止

## 4. 監査コメントの基本フォーマット

監査は原則として以下の順:

### 4.1 まず評価

- 構造として何が立っているか
- 実装上何が守られているか
- 観察として何が増えたか

### 4.2 次に懸念

- AI がどこを誤読しうるか
- Summary 化でどこが危険か
- 実装へ落とす時にどこが曖昧か

### 4.3 最後に修正

- 直す必要がある場合のみ
- 誰向けの文書かを明示
- どの語をどう置き換えるか
- 具体的メリットを添える

## 5. 避けるべき失敗 4 パターン

| 失敗 | 内容 |
|---|---|
| 5.1 批判のための科学 | 懐疑自体を価値化し、探索を前に進めない監査 |
| 5.2 字面反応 | 語の強さだけで制動する、読者・用途・実装層を確認しない |
| 5.3 比喩と仕様の混同 | 比喩的に有効な表現を仕様違反と誤認 |
| 5.4 慎重さの誤読 | 強い表現だけで「方法論も雑」と推定する (ESDE の方法論は厳しい) |

---

## 6. GPT 監査の役割定義 (一文)

> **GPT 監査は、Taka の比喩的・哲学的な推進力を削るのではなく、それを仮説・実装・観察へ切り分け、AI が誤読しない形に翻訳する役である。**

これは 3 役分離における GPT の役割を精密に定義したもの。単なる「制動役」ではない。

---

## 7. 監査が「弱める」提案をする時の自問 4 項

修正提案を出す前に必ず自問:

1. これは誰向けの修正か
2. 何の誤読を防ぐのか
3. その修正で何が具体的に良くなるのか
4. その修正は探索力を削いでいないか

**4 項全てに答えられないなら、その修正提案は出さない**。

## 8. Claude への適用

本指針は GPT 監査のためだけでなく、**Claude が資料作成する時の自己規律**としても機能する。

### 8.1 Claude の癖への構造的対処

Claude の既知の癖:
- 意味を盛る
- 判断を前に出す
- 整理を過剰にする
- 論点を並列して判断回避する

本指針が Claude に与える歯止め:
- **§2 読者明示**: 資料作成時に「誰向けか」を先に書く
- **§1.3 先に切り分け**: 比喩/仮説/実装/観察のラベルを意識
- **§4.3 修正は必要時のみ**: 修正提案を乱発しない
- **§7 自問 4 項**: 判断を前に出す前の自己規律

### 8.2 Taka 発言の扱い

- **原文引用 (>)** を基本とする
- Claude の言い換えで意味を変質させない
- 比喩は比喩として扱い、仕様に即座に落とさない
- 「構造が先、定義は後」の Taka 哲学を尊重

### 8.3 資料作成時のチェックリスト

Claude が新しい資料を作る前に確認:

- [ ] 誰向けの資料か明記したか
- [ ] Taka 発言は原文引用で保存したか
- [ ] 比喩と仕様を分けたか
- [ ] 推奨を前に出しすぎていないか
- [ ] 判断を並列提示で逃げていないか (逆の癖)
- [ ] 未確定部分を未確定のまま残したか

## 9. 比喩ラベリングの運用 (軽量版)

新しい比喩が Taka から出るたびに、**資料末尾**に簡易記録:

```
### 比喩ラベル記録 (本資料で出現したもの)

| 比喩 | 発言日 | 対応する観察事実 | AI 向け操作語 |
|---|---|---|---|
| 摂食行動 | 2026-04-23 | 片方向 E3 接触 77% | 片方向 ghost 接触 |
| 意識の原資 | 2026-04-23 | Q 消費 = 認知増加仮説 | Q 消費と認知的資源の対応 |
```

一覧化 (全比喩を集約する単一テーブル) は管理負担が大きいので**作らない**。資料ごとに末尾へ軽量記録するだけ。

### 12.3 アリズムの運用方法論 (v9.18 Taka 2026-04-24 明文化)

> 間違いの価値を高める、という反転ができてこそアリズム

- 実装が「間違い」でも削除しない (「ない」ではなく「ある」として扱う)
- 価値を反転させて活用する (別の意味を見出す)
- v9.18 の V_unified / theta_distance は物理層の時間発展 Baseline として保持、意識層実装時の対比指標に

この方法論は GPT 監査運用指針 v1 の範囲を超えるが、指針の精神 (探索を削がない、切り分けて翻訳する) と整合。

## 14. GPT 短報: Primitive → Developmental 移行 (2026-04-24)

### 14.1 背景

v9.18 段階 5 完了後、Taka が層の混同を指摘 (V_unified が物理層を測っていた、Taka の「統合」は認知層+意識層の協働)。GPT が短報で運用改善を提案。

### 14.2 GPT 短報の診断

v9.18 の食い違いの原因:
> v9.18 を Primitive の延長として扱ったため、AI 側が物理層や既存認知層の延長として自然に解釈した。もし最初から v10.x = 意識層と明示していれば、今回のような「物理同期を統合と誤読する」方向には進みにくかった。

**層ラベル不足**が原因。指針 v1 §5.3 (比喩と仕様の混同) の類型だが、**バージョン名レベル**での予防が不足していた。

### 14.3 GPT 提案: 探索帯域の明示

> v10.x 化は定義の固定ではなく、探索帯域の明示である。

これは指針への新しい追加原則:
- **構造 = 探索帯域 = 層**を先に明示 (バージョン名とディレクトリで)
- **定義 = 機能の詳細**は後で Taka の直感が詰める
- 主題ラベルを看板として先に立てることで、AI の解釈ドリフトを構造的に予防
- Taka 哲学「構造が先、定義は後」の運用的翻訳

### 14.4 Taka 判断 (2026-04-24)

- GPT 提案を採用
- フェイズ名: **Developmental** (conscious ではなく)
- ディレクトリ: `developmental/v10X/`
- 開始: Now
- 旧 v10 の再付番: 不要 (Taka が記憶)

Taka 発言原文:
> 名称は conscious と言いたいところだが、developmental を推す。理由は、このフェイズで始めて意識という私たちが掲げてきた対象のようなもの、を扱えるようになることを目標としているからだ。これは、cognition という phase 名をつけたものの、実際は存在層を扱っていたという過去 (夢を見すぎた) の経験から、本来の正しい位置付けを自覚することを目的としている。

### 14.5 Claude への適用

v10.x Developmental フェイズ以降、Claude が資料作成時に:

1. **草案冒頭で層を明示**: 「このフェイズは意識層の発達を扱う」を冒頭に固定
2. **物理層と意識層の混同を避ける**: V_unified 相当の物理層指標を作らない、作るなら明示的に物理層 Baseline と記述
3. **到達宣言を避ける**: 「意識を実装した」「統合が成立した」等の語を使わない
4. **フェイズ名と層名の対応を意識**: Developmental = 認知層 + 意識層の発達を扱うフェイズと明示

### 14.6 指針 v1 との関係

本 §14 は指針 v1 の拡張ではなく、**指針 v1 の限界の記録 + 運用改善の方針**。

- 指針 v1: 比喩と仕様の混同への個別対処 (§5.3)
- GPT 短報: **バージョン名レベル**での構造的予防 (§14)

両方を併用する運用。指針 v2 の正式化は Developmental フェイズの経験後に検討 (Taka 判断待ち)。

### 14.7 指針 v1 と GPT 短報の統合運用ルール

1. 新しいフェイズ (バージョン) を開始する時は**必ず主題となる層を明示**する (§14.3)
2. 比喩を操作語に翻訳する前に**どの層の話かを検証**する (指針 v1 §5.3 + §14)
3. 2 AI 一致時でも**層の整合性**を確認する (v9.18 の教訓)
4. 実装が「間違い」と判明した時は**削除せず保留**して価値反転の可能性を探る (アリズム運用方法論)

### 14.8 Developmental フェイズでの適用

v10.x 以降、本指針 + §14 の両方を適用:
- 草案冒頭: 「このフェイズは意識層の発達を扱う」を固定
- Code A 指示書: 操作語レベルで物理層と意識層を分離

- 比喩ラベリング: 比喩の層を明示 (物理層 / 認知層 / 意識層 / 方法論)

## 15. 二層 bit-identity 検証 (Code A 指摘 2026-04-26)

### 15.1 層 A (v10.x 内部 bit-identity)

同 seed で 2 回 run → 出力が完全一致するか

```
smoke 段階で必ず実施:
  ./smoke_v102_a (1 run)
  ./smoke_v102_b (1 run)
  diff -r smoke_a smoke_b (全 CSV MD5 一致)
```

意義: 内部決定論性の確認。RNG ストリームの分離不備や非決定的処理の検出。

- 観察軸の追加は判定枠外の整理仮説を生む可能性があり、それ自体が finding になる
- Code A の自由度を上げる規律ではない (Taka 承認は維持)

### 35.2 運営メタ規律 8 項目 (GPT 第三回監査提示、Taka 整理)

#### 規律 1: オープン調査とクローズ調査を固定方針にしない

ESDE は白地図を行く要素が強く、オープンにすべきフェイズとクローズにすべきフェイズを固定的に決めるのは無理がある。状況依存で判断する。

#### 規律 2: 追加調査を開く時は理由を明示する

以下のいずれかの理由を持って初めて追加調査を開く:
- 前提崩れの補正 (実測で主題の前提が崩れた場合)
- 観察軸不足の補完 (集団平均の罠等で構造が見えない場合)
- 次フェーズ設計素材の確保 (v10.x+1 で必要な素材が見えた場合)
- 平均化による誤認の回避 (n_core 別層化等が必要な場合)

理由が明示できない追加調査は「気持ちいい観察の延長」のリスクがあり、避ける。

#### 規律 3: 平均で潰れる構造は必ず層化を検討する

n_core 別層化解析必須 (§34 規律 #37) はその典型例。集団平均は cid 集団の n_core 分布に支配されやすく構造的事実を見えなくする。

#### 規律 4: 閾値は真理ではなく運用上の仮置きとして扱う

age_target、bin 区切り、効果量基準等の閾値は実測で必要なら調整する。閾値を「真理」として扱うと観察構造を歪める。

#### 規律 5: 整理語は観察事実と分ける

仮ラベル (応答性窓 / 形成と硬化の力学 / リバースエンジニアリング 等) を使う場合、観察事実 / 整理仮説 / 未解明 の 3 段階分離を徹底する。判定語ではなく整理語として明示。

#### 規律 6: 主題終了条件は置くが、その前提が実測で崩れた場合は再開を許す

打ち切り条件は事前定義するが、実測で前提が崩れたら主題射程を再考する余地を残す。「もっと見れば見えるかも」を禁止する一方、「観察した結果、主題自体の前提が崩れた」場合は再開を許可。

#### 規律 7: 監査や整理は、閉じる妥当性だけでなく、開く妥当性も評価する

「ここで閉じるべき」だけでなく「ここで開くべき」も Web Claude / 2 AI / Code A の判断対象。Web Claude が無自覚に「結論を急ぐ」癖を補正する。

#### 規律 8: 最終的な開閉判断は、現場感を持つ人間側に残す

研究方針判断 (主題確定、観察軸の追加要求の受諾等) は Taka に集約する。Web Claude / 2 AI / Code A は判断材料を提示する役割で、最終判断には踏み込まない。
